# Personal Guitar Coach — правила роботи

## Призначення

Створюємо нативний macOS-додаток для самостійного навчання гри на гітарі: текстові уроки, інтерактивний гриф, табулатура, практика з реальним аудіовходом, метроном, тюнер, оцінки та рекомендації. Увесь користувацький інтерфейс і навчальний контент доступні англійською та українською.

Перед змінами прочитай [опис продукту](docs/PRODUCT.md), [архітектуру](docs/ARCHITECTURE.md), [план задач](tasks/README.md) і файл поточної задачі. Для аудіо та оцінювання додатково прочитай [контракт аудіо](docs/AUDIO-AND-ASSESSMENT.md). Фактичний стан реалізації визначають код, тести та докази у файлах задач.

## Уточнення користувача від 2026-09-09

- Реалізувати всі 22 задачі. Для кожної: окрема гілка `codex/NN-description`, опублікована на GitHub, реалізація, перевірки, локальний review, виправлення, PR та merge. Користувач явно дозволив ці дії; додаткове підтвердження на кожен PR/merge не потрібне.
- Основний інструмент — електрогітара через інтерфейс. Підтримувати також акустику через мікрофон або п'єзознімач; джерело сигналу має бути явним.
- Усе, що потребує користувача або його обладнання, переносити до [фінальної перевірки](docs/USER-VALIDATION.md), після реалізації всіх задач. Це не блокує залежні програмні задачі або merge перевіреного коду.
- Неперевірені hardware-критерії не називати виконаними. Статус `pending_user` означає: код реалізовано та змерджено, апаратні/користувацькі перевірки лишилися відкритими. На GitHub issue лишається відкритим, Project — `In review`, доки evidence не отримано.
- Розповсюдження не планується: App Store, Developer ID, notarization та публікація не входять у поточний обсяг. Потрібна локальна працездатна Release .app з ad-hoc підписом.
- Локальний review кожної задачі записувати в `docs/reviews/NN-review.md`: область перевірки, конкретні знайдені проблеми та виправлення, докази повторної перевірки. Не заявляти незалежний review, якщо його виконав той самий агент.

## Межі першої версії

- Swift + SwiftUI, справжній macOS app target; AppKit лише для потрібних системних інтеграцій. Без Electron, вебобгортки та сервера для основних функцій.
- Початковий deployment target — macOS 14+. У задачі 01 перевірити сумісність і зафіксувати конкретну версію Xcode/Swift; не залежати від beta SDK.
- Шестиструнна гітара, 0–24 лади, Standard / Drop D / D Standard і власний стрій.
- Оцінювання першої версії — послідовні окремі ноти чистої гітари. Акорди можна показувати в уроках і на грифі, арпеджіо можна оцінювати. Одночасне звучання акорду не видавати за перевірене розпізнавання.
- Основні сценарії працюють офлайн. Аналіз аудіо виконується локально; сирий звук за замовчуванням не зберігається.
- Songsterr — орієнтир для читабельної табулатури й курсора відтворення, а не вимога копіювати сервіс або його контент.

## Архітектурні правила

- Domain містить музичну модель та чисті правила; не імпортує SwiftUI, AVFoundation або конкретне сховище.
- Одна модель `TuningProfile` / `FretPosition` / `MusicalEvent` / `Exercise` живить гриф, табулатуру, уроки, тюнер і практику. Не дублювати обчислення нот у views.
- Нумерація струн: 1 — найтонша, 6 — найтовща. MIDI 60 = C4; використовувати реальну висоту звучання. Стрій у документах завжди підписувати порядком струн.
- Відкрита струна — лад 0; приглушена струна — окремий стан, не від'ємний лад і не MIDI-нота.
- Музичний час зберігати в цілих ticks із явно визначеним PPQ. Host time / sample time конвертувати лише на межі аудіосистеми. Не порівнювати sample counters різних пристроїв без перетворення.
- View state оновлювати на MainActor. Audio callback має бути обмеженим за часом: без UI, await, Task creation, логування, файлових операцій, блокувальних locks і динамічних алокацій. DSP працює поза callback через попередньо виділений bounded buffer.
- Один координатор володіє життєвим циклом аудіо. Тюнер, практика та preview не запускають конкуруючі capture pipelines.
- Метроном планувати за аудіогодинником. UI timer дозволений для відображення, але не як джерело моментів кліків чи оцінки ритму.
- Підключення та від'єднання інтерфейсу, зміна sample rate, sleep/wake і permission denial — штатні стани продукту.
- Залежності додавати лише для конкретної потреби, перевіривши підтримку macOS, ліцензію та вартість супроводу. Точний аудіобекенд обрати за результатами задачі 02.

## Правдивість результатів

- Звук сам по собі не доводить, на якій струні та яким пальцем зіграно ноту. Візуалізація показує очікувану аплікатуру, оцінка — чутну висоту і час.
- Не показувати оцінку успішності за відсутності валідного аудіо. `insufficientSignal`, `interrupted`, `uncalibrated` та звичайні музичні помилки мають різну семантику.
- Кожен результат зберігає версії вправи, строю, алгоритму й калібрування. Не переобчислювати старі оцінки мовчки після оновлень.
- Рекомендації спираються на виміряні помилки. Не вигадувати діагнози щодо техніки, положення руки або пальців.
- Моки, синтетичні сигнали та реальний USB-інтерфейс позначати окремо у звітах перевірки. Не називати mock demo завершеною аудіоінтеграцією.

## Локалізація та доступність

- Кожна нова функція одразу має `en` та `uk`: labels, меню, Settings, помилки, accessibility labels, уроки, результати й рекомендації.
- UI-рядки — String Catalogs; навчальні тексти — локалізовані ресурси зі стабільними ID. Не використовувати перекладений текст як ключ збереження.
- Мова: System / English / Українська. Перемикання не скидає відкритий урок або прогрес. Не конкатенувати перекладені речення.
- A–G з октавами — однозначні позначення висоти в обох мовах; пояснення можуть містити «до», «ре» тощо. Не плутати локаль мови з музичним строєм.
- Клавіатурна навігація, VoiceOver, світла/темна тема, достатній контраст. Колір не є єдиним індикатором правильності або вибраної ноти.

## Процес реалізації

1. Перевір git status, залежності задачі та наявні реалізації. Зберігай сторонні зміни.
2. Реалізуй обмежений вертикальний сценарій відповідно до критеріїв задачі. Рутинні оборотні рішення приймай самостійно в межах запиту.
3. Оновлюй файл задачі й індекс однаково: `todo` → `in_progress` → `done` або `pending_user`; `blocked` лише з конкретною причиною. `done` потребує доказів приймання. `pending_user` не блокує подальшу реалізацію за прямою вказівкою користувача.
4. Додавай змістовні перевірки музичної математики, DSP, matching, persistence і переходів стану. Для косметичних змін достатньо відповідної візуальної перевірки.
5. Запускай релевантні build/test-команди. У README мають бути фактичні команди після scaffold; до його появи не стверджуй, що build/test проходять.
6. Після роботи коротко опиши результат, виконані перевірки та реальні обмеження. Апаратні перевірки без пристрою залишай відкритими.

Гілки за потреби мають префікс `codex/`. Не комітити ключі підпису, приватні записи або згенеровані build artifacts. Не розширювати задачу до акаунтів, хмари, платежів чи AI-сервісів без відповідного запиту.

## Definition of Done

- Критерії задачі виконано, залежності закрито, перевірки та їх результати записано.
- Обидві локалізації та доступність покривають новий користувацький сценарій.
- Реальні помилки мають зрозумілі UI-стани; немає підробленої успішності.
- Зміни моделей мають версіонування та міграції, якщо вже існують збережені дані.
- Документація відповідає коду; невиконані hardware/release gates явно відкриті.
